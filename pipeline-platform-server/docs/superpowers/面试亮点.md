# 面试亮点积累(随任务更新)

> 用途:写简历/准备面试时,从这里取材统合。每完成一个任务,同步补一节。
> 用法:每个技术点配「一句话亮点」+「面试官可能问什么、怎么答」。

## 项目总览(面试开场 30 秒,先背熟这个)

**一句话定位**:我给个人博客做的一个 AI 智能助手,会多轮对话、能回答「关于我」的问题、还会读用户上传的 PDF/Word 文档,已经上线生产环境(ai-myhome.space)。

**开场白模板**(照着说,30 秒):
「这是一个 AI Agent 项目,基于 LangGraph + RAG 做的。它能干三件事:第一,像豆包一样多轮聊天,有账号有记忆;第二,关于我的简历问题,它通过检索我的知识库来回答,而不是瞎编——回答下面还会列出参考资料,点开能核对;第三,用户上传 PDF/Word 文档后,它可以读文档回答问题。整套是我独立开发的,Python + FastAPI 后端,PostgreSQL + pgvector 做向量检索,Nuxt 3 前端,已经上线,前后端加起来 118 个自动化测试。」

**数字速览**(面试时随口带出,显得真实):
- 简历知识库 18 块切片;检索标定集 13/13 全对
- 文档解析实测 6 秒/峰值 770MB(2G 服务器)
- 4 万字上下文可压到 3 千字,对话记忆不丢
- 118 个自动化测试,TDD 开发;cron 自动部署,push 即上线

**技术栈一句话**:Python + FastAPI(接口)+ LangGraph(Agent 大脑)+ PostgreSQL/pgvector(向量检索)+ MinerU(文档解析)+ Nuxt 3/Vue 3(前端)

## Task 2 骨架

- **技术点**:FastAPI + /health 健康检查 + 测试先行
- **一句话**:先立一根「能跑的最小骨架」—— 健康检查接口是部署验证的锚点(线上每次部署都打它确认服务活着)

## Task 3 知识源

- **技术点**:profile.md(简历文字版,人写的结构化 Markdown)
- **一句话**:知识库的「源文件」是人可读的 Markdown,不是数据库——内容想改,改文件重灌一遍,数据库永远只是它的「向量投影」

## Task 1 环境准备

- **技术点**:Python 3.12 + uv(现代 Python 包管理,替代 pip/venv 一步到位)、Docker 跑 pgvector、SSH 隧道
- **一句话**:数据库只监听 127.0.0.1 不暴露公网,开发机通过 SSH 隧道 + 密钥免密访问 —— 安全习惯
- **问答**:「数据库为什么连 127.0.0.1?」→ 最小暴露面:不监听公网、无密码登录(密钥)、SSH 隧道加密通道

## Task 4 切片(chunking)

- **技术点**:LangChain 两段式切片(MarkdownHeaderTextSplitter 管结构 → RecursiveCharacterTextSplitter 管长度)、中文自定义分隔符、标题进 metadata 面包屑(section)、重叠窗口、短节合并限同一 h2
- **一句话**:标题当元数据带进每块,检索命中时能告诉大模型「这段来自简历哪一节」
- **问答**:「怎么切块?」→ 结构 + 长度两段式;800 字上限、100 字重叠;中文标点要自己加(库默认只有英文标点)

## Task 5 入库与检索

- **技术点**:pgvector 双写双表(豆包 1024 维 / 智谱 2048 维,一表一模型)、embedding 提供方注册表、HNSW 向量索引(vector_cosine_ops)、自动降级
- **一句话**:两个 embedding 模型各存一张表,主提供方故障自动降级;「查不到」不算故障不降级
- **问答**:「为什么双写?」→ 单模型单点故障风险;维度不同所以分表。「为什么 HNSW?」→ 近似最近邻,大数据量下比全表扫快几个量级,个人项目用它是提前养成正确习惯

## Task 5.5 混合检索(两路召回 + RRF)

- **技术点**:pg_trgm 三元组、GIN 倒排索引、word_similarity(短问长文打分)、RRF 排名融合、两路召回
- **一句话**:向量管「意思像不像」,关键词管「字面有没有」,RRF 只比排名不比分数
- **问答**:见下方「面试高频问答」前 4 条 —— 全是这个任务的内容

## Task 6 LangGraph Agent(工具调用循环)

- **技术点**:状态/节点/边/条件边、`create_react_agent` 库版本、`bind_tools` 工具声明、工具返回 `Command` 写状态、`InjectedToolCallId`
- **一句话**:「LLM 决定调工具 → 执行 → 把结果还给 LLM 再答」的循环就是 Agent 区别于普通聊天机器人的本质;来源收集靠状态扩展(sources 字段)+ 工具返回 Command 写进去
- **踩坑(面试加分项,真实经历)**:langgraph 1.2 的 create_react_agent 强制要求状态带 `remaining_steps`,但 ①TypedDict 默认值不生效,缺失从 0 起步 ②配 `operator.sub` 会把输入也过一遍运算,越传越负 ③`"add_messages"` 字符串注解已失效要传函数 ④0 步时其内部「空 tool_calls 判空为真」bug 会把正常回答替换成 Sorry。解法:薄壳包装,把库的坑关在模块里 —— 「用库不迷信库,最小用例先验证」
- **问答**:「create_react_agent 内部做了什么?」→ 见 graph.py 底部注释的手写三节点版,一层层能讲出来

## Task 7 SSE 流式接口 + 博客转发

- **技术点**:SSE(Server-Sent Events)、LangGraph `astream_events` v2 事件流、OpenAI 兼容格式契约、向后兼容协议设计、薄壳转发(Web ReadableStream → Node PassThrough 桥接)、`AGENT_BASE_URL` 环境变量
- **一句话**:换实现不换契约 —— Agent 服务保持 OpenAI SSE 格式,博客前端解析代码**一行没改**;新增 `event: sources` 事件块,老解析器只认 `data:` 行自动跳过
- **踩坑(真实经历)**:①计划里写的工具节点名 `call_tools` 是手写版的名字,库版本对不上,来源事件永远发不出 —— 真跑事件流才发现最终状态在 `on_chain_end`(name=LangGraph)里;②`tools` 节点的 output 是 Command 列表不是 dict;③Windows curl 传中文 JSON 编码乱码,要落文件 `--data-binary`;④Nuxt dev server 未就绪时打接口返回 503 假象
- **问答**:「SSE 和 WebSocket 的区别?」→ 都是长连接,SSE 单向(服务器推)、基于普通 HTTP、自动重连;WebSocket 双向全双工。聊天场景 SSE 更轻。「为什么要保持 OpenAI 格式?」→ 前端零改动 + 生态兼容,未来换模型/换后端都只动服务端

## Task 8 前端来源展示

- **技术点**:SSE 多事件类型解析(`event:` 行决定后面的 `data:` 行怎么解读)、自定义事件做向后兼容、来源渲染、「故意不显示分数」的取舍
- **一句话**:证据要能验证 —— 回答下方列出 `profile.md · 项目经历 / 苏打爱生活 H5…`,访客能顺着回查简历原文,这是「懂我的助手」区别于「AI 瞎聊」的地方
- **问答**:「SSE 怎么同时传正文和来源?」→ 正文沿用 OpenAI 默认 data 事件(前端解析零改动),来源另开 `event: sources` 事件块,老解析器只认 data 行天然跳过 —— 协议上做加法不做改动
- **取舍**:混合检索后 score 是 RRF 排名分(`1/(60+rank)` 累加),不是置信度。显示「相关度 2%」会让访客以为不相关 —— 宁可不显示

## Task 9 部署上线(腾讯云 + pm2 + Nginx + Vercel)

- **技术点**:pm2 进程托管 + 开机自启、SSH deploy key(只读)、腾讯云 PyPI 内网镜像、Nginx 反代 `proxy_buffering off`、Vercel 函数 `maxDuration`、环境变量配置分离、首字节/总耗时流式验证法
- **一句话**:服务绑 127.0.0.1 只经 Nginx 出门;pm2 崩了自动拉起;换域名只改环境变量不改代码
- **踩坑(真实经历)**:①Vercel 免费版函数默认 10s 超时,LLM 回答要 15~30s 会被掐死 —— 配 `maxDuration=60` 时发现这个版本 nitro 的 `routeRules.maxDuration` 是死配置(源码里只展开 `nitro.options.vercel.functions`),读 nitro 源码定位;②服务器直连 pypi.org 被限速(15s 才开首页),换腾讯云内网镜像后 1.5s 解析完;③SSH 客户端默认不认自定义文件名的密钥,要写 `~/.ssh/config` 的 IdentityFile;④验证流式是否被中间层缓冲:看首字节时间,0.14s 首字节/11.34s 总耗时 = 真流式,缓冲的话两者相等
- **问答**:「Nginx 为什么要 proxy_buffering off?」→ 默认攒一批再发,SSE 要的是吐一个字立刻到,关掉才流得起来。「pm2 是干嘛的?」→ 进程守护:崩溃自动拉起、开机自启、日志收集,三个字:别裸跑
- **自动部署(拉取式 vs 推式)**:为什么不用 GitHub Actions 推式、用 cron 拉取式?→ 国内到 GitHub 网络不稳,推式断了要重推、runner 回连国内服务器也慢;拉取式每 5 分钟重试、零外部依赖。版本对比不手写版本号文件(会漏改),直接用 git 自带 commit 哈希 —— 这本身就是版本号
- **自证清白的工作方法**:改检索逻辑后真库结果变了,不急着定罪 —— `git stash` 跑旧代码对比,发现同一份旧代码两次运行排名也不一样,证明是 embedding API 的微小随机性(近邻块分数差 0.000x),不是重构引入的回归

## Task 10 M2(MCP Server)

- **技术点**:MCP 协议(Model Context Protocol)、官方 Python SDK 2.x(MCPServer)、stdio 传输、工具注册复用、依赖注入做可测性
- **一句话**:同一个 `search_profile` 函数两个身份 —— LangGraph 工具(博客 Agent 用)+ MCP 工具(Claude Code 用),「一套能力,多个入口」;MCP 就是 AI 工具的 USB-C,提供一次,各家 AI 应用都能插
- **问答**:「MCP 是什么?」→ 开放标准,解决「每家 AI 应用各写各的工具接入」的碎片化 —— 类比 USB-C 统一充电口。客户端(Claude Code/Cursor/Desktop)经 stdio 或 HTTP 连你的 Server,拿到工具列表,需要时调。「为什么函数一行没改?」→ 工具层和入口解耦:tools.py 只有检索逻辑,绑 LangGraph 或注册 MCP 都是在外面包一层
- **踩坑(真实经历)**:`uv` 装到 mcp 2.x —— `FastMCP` 不存在了(报错信息直接给迁移提示:改名 `MCPServer`);2.x 连测试接口也变了(内存会话 helper 没了),改用 `MCPServer` 自带的 `list_tools`/`call_tool` 服务端直调做单测,协议层用 `stdio_client` 起真进程验证。教训:新大版本先探测 API 再写代码,报错信息本身就是最好的文档
- **验证分层**:单测(FakeKB 注入,不连库)→ 协议级(stdio 真握手 + list_tools)→ 真调用(embedding API 200 + 真库返回简历原文)—— 三层递进,每层跑通再进下一层

## Task 11 M3.1 会话记忆(LangGraph checkpointer)

- **技术点**:LangGraph checkpointer(状态持久化)、PostgresSaver、thread_id、访客/登录双模式请求组装、msgpack 序列化白名单
- **一句话**:Agent 从「失忆」变「有记忆」—— 前端只发最新一句,历史由 checkpointer 按 thread_id 从 PG 恢复;追问「那第二个呢」接得上,这就是豆包式连续对话的技术底座
- **产品决策**:访客不持久化会话(行为与无记忆版一致),登录用户才带 session_id —— 门槛在请求层,一个 `build_inputs` 函数两种模式,后端能力对访客透明
- **验证方法(对照实验,面试加分)**:同 thread 追问「那第二个呢」准确数出项目;无历史对照 thread 直接问同一句,LLM 硬猜还编细节 —— 记忆的价值被对照实验证明,而不是「看起来能接上」
- **踩坑(真实经历)**:①checkpoint-postgres 3.x 的 `from_conn_string` 返回 AsyncIterator,必须 `async with` 进入(2.x 用法失效)②Windows psycopg 异步不认 ProactorEventLoop,要换 Selector 策略 ③图状态里的自定义 dataclass 存 checkpoint 要显式加 msgpack 白名单,当前只 warning、未来版本直接拒绝 —— 读 warning 提前修,不等它炸;④GBK 控制台打印 emoji 崩(LLM 回答带 😂 就会踩)⑤**部署事故链**(生产实战):pm2 里的 `uv run` 自动 sync 改写 `uv.lock` → 文件变脏 → cron 自动部署的 `git pull` abort → 服务器卡旧版本,新代码上不去。排查用了 git reflog + 部署日志还原时间线;修复 = deploy.sh 里 pull 前 `git checkout -- uv.lock`(纯部署目录无手改,直接还原兜底)
- **问答**:「checkpointer 是什么?」→ LangGraph 把图的状态(对话历史)按 thread_id 快照存库,每次请求先恢复再跑,跑完再存 —— 状态机 + 持久化。「为什么访客无记忆?」→ 产品决策:门槛在请求层,访客不带 session_id 就不挂 checkpointer,能力对访客透明,登录后再开

## Task 12 M3.2 账号体系 + 会话列表

- **技术点**:bcrypt 密码哈希、JWT(HS256)签发/校验、FastAPI Depends 鉴权依赖、会话归属防线、Vue 组合式 composable、Nuxt 薄壳转发透传鉴权
- **一句话**:conversation.id 直接当 checkpointer 的 thread_id —— 会话列表里的每条会话和它的对话记忆用同一个编号,零映射;「记忆归属账号」:换设备登录,历史和会话列表都在
- **归属防线(安全设计,面试必讲)**:所有会话 SQL 都带 `WHERE user_id = %s` —— 取不到/删不掉别人的会话,统一返回 404 不暴露存在性;注册用唯一约束兜底并发,重复用户名 409
- **分层可测**:auth.py 纯函数(哈希/签名)→ 单测 5 个;401/422 拦截(TestClient,不连库)→ 4 个;SQL 真库验证(auth_check 7 项)三层递进
- **踩坑(真实经历)**:①Vue 模板里「普通对象内的 ref」不会自动解包 —— `auth.user` 是永远 truthy 的 Ref 对象,`v-if` 恒真渲染错模板(SSR 和客户端都错);解构成顶层 ref 才自动解包 ②langgraph-checkpoint 3.x 的 CheckpointTuple 没有 .values(老文档写法),消息实际在 `checkpoint['channel_values']` ③uvicorn 0.36 在 Windows 上硬编码 ProactorEventLoop(源码里直接 return,不理会 set_event_loop_policy),psycopg 异步不认 —— 用 run 的 loop 参数传 SelectorEventLoop 覆盖;生产 Linux 无此问题

- TDD:先写失败测试 → 看它失败 → 最小实现 → 看它通过
- 真库标定集:13 个「有预期答案的问题」做回归,每次改检索都要跑一遍
- 文档体系:spec(设计)+ plan(施工)+ 人话版(进度板)
- 真库验证抓到过单测抓不到的 bug(word_similarity 参数顺序)
- **embedding 非确定性(真库对比实验发现)**:同一问题连打两次,近邻两块的排名可能互换 —— 余弦分只差 0.000x,而 embedding API 每次返回的向量有微小随机性。改检索逻辑后对比新旧代码时,要先跑同代码多次排除这个噪音,才能定罪

## Task 13 M4(MinerU 文档助手)

- **技术点**:MinerU 4.x 双档位(PDF→basic 纯 CPU ONNX / Office→flash 本地确定性解析)、独立解析服务(8001,串行队列 + 名额制 429)、临时库(session_key,24h 清理)/永久库(user_id)两级存储 + 按意图 promote、混合检索复用(向量 + 关键词 + RRF)、动态系统提示点名会话文档、浏览器直传 25MB + CORS
- **一句话**:RAG 从「只会读自己的简历」升级到「会读用户上传的文件」—— 上传 → 解析 → 切片入库 → 问答命中,且文档归属按会话/账号两层隔离
- **踩坑(真实经历)**:①`.doc` 上传报「Tier 'basic' is only supported for PDF and image files; 'doc' files use tier 'flash'」→ 按后缀选档位;②入库 source 硬编码 `"upload"` → 参考资料显示认不出是哪份文档,改为存真实标题;③MinerU 解析 docx 标题自带 Markdown 星号(`**个人登记表**`)→ `clean_section` 入库前清洗;④智谱免费额度 429 拖垮整个入库 → 按 provider 容错,单表失败不炸(检索端自动降级);⑤2G 服务器:basic 档实测 6s/峰值 770MB,串行 + 名额 3 超了 429,防算力被吃满
- **问答**:「为什么解析单独一个服务?」→ 解析是 CPU 密集 + 耗时(秒级)的活,和问答主服务放一个进程会堵事件循环;拆到 8001,串行队列保证一次只解析一个。「文档存多久?」→ 临时库 24 小时自动清理;用户明确说「长期记住」且确认,才 promote 进永久库 —— 按意图入库,不擅自永久存。「flash 和 basic 什么区别?」→ flash 是确定性文本提取(不跑神经网络,快、省),basic 是 ONNX 小模型 OCR;PDF/图片用 basic,Office 格式只能 flash

## Task 15 记忆治理(上下文压缩)

- **技术点**:双层阈值(手动 20000 字亮按钮 / 自动 40000 字强制压)、LLM 摘要(200 字上限,取材最近 3 万字)、压缩写回 checkpointer、SSE 每轮回传最新字数(event: chars)
- **一句话**:每轮把全部历史重发,越聊越贵越慢,最终超窗口 —— 手动按钮为主 + 自动兜底,压成「摘要 + 最近 6 轮」
- **踩坑(真实经历)**:①checkpointer 直接 aput 写同版本号会被**静默拒绝**(线上实测:压缩后读回还是旧历史)→ 先 `adelete_thread` 再 aput;②前端按钮原来按「显示文字」数字数,工具轮内容(每次文档检索几千字)不算 → 按钮几乎永不亮;改为服务端统一口径,`/messages` 返回真实字数 + 阈值,SSE 末尾 chars 事件实时更新;③摘要只取最后 8000 字时,历史 2 万+ 的早期身份/结论全丢 → 取材上限提到 3 万字
- **问答**:「为什么 20000 字才提示压缩?」→ 8000 字 ≈ 1 万 token,每轮重发就一两分钱、速度无感,太早弹按钮纯属打扰;2 万字(≈3 万 token)开始有点慢有点费,但离 40000 兜底还有距离。「压缩会不会丢记忆?」→ 摘要强制保留①用户是谁②关键结论③未完成事项,再加最近 6 轮原文兜底;线上实测 4 万字 → 3 千字,继续追问接得上。「为什么手动 + 自动双层?」→ 全自动会在不该压的时候压(打断节奏),全手动用户会忘(窗口爆掉)—— 手动给控制感,自动兜底线

## 2026-10 补丁与修复(小而典型)

- **pgvector hnsw 硬限制**:索引最多 2000 维,智谱 embedding 2048 维建索引直接 ProgramLimitExceeded(表建一半)→ 超限跳过向量索引,表小走精确扫描。教训:库的硬限制要在建表路径上处理,不能等线上炸
- **注册入口前后端双关**:只藏前端按钮挡不住直接打 API(XSS 也能把按钮弄回来)→ 后端 403 才是真关闭;前端按钮只是体验层
- **退出登录全量清状态**:会话、聊天、上传反馈(含上一账号的文档名)、登录表单一次清干净 —— 换账号零残留
- **参考资料展示**:默认折叠一行,点开才看明细;同文件章节合并(碎切片文档不刷屏),计数与明细对得上;不显示 score(RRF 排序分不是置信度,显示会误导)

## 面试高频问答(边做边攒)

1. **问:纯向量检索有什么缺点?** 答:对缩写/专有名词不敏感 —— 向量算语义相似,「bdms」这种词的字面信息被稀释,会命中语义像但无关的块
2. **问:怎么解决?** 答:混合检索:加一条 pg_trgm 关键词路做字面匹配,两路召回用 RRF 融合
3. **问:RRF 是什么?为什么不用加权求和?** 答:Reciprocal Rank Fusion,按排名融合(1/(60+rank) 求和)。两路的分数不是一个尺子没法直接加,排名可以
4. **问:word_similarity 和 similarity 的区别?** 答:分母不同 —— similarity 用长文本当分母,短问长文永远趋近 0;word_similarity 用查询词当分母,衡量「查询词在块里出现几成」
5. **问:pg_trgm 和 GIN 索引是干什么的?** 答:pg_trgm 把文本切成连续三元组;GIN 是倒排索引(词 → 出现位置),专门加速「哪些行包含某个值」这类查询,和 B+ 树是两种思路
6. **问:为什么数据库只监听 127.0.0.1?** 答:最小暴露面 + SSH 隧道访问,外网连 5432 都碰不到
7. **问:Agent 和普通聊天机器人有什么区别?** 答:Agent 有工具调用循环 —— LLM 自己决定「要不要查资料、查哪个」,循环到能回答为止;聊天机器人只会凭记忆答。本项目用 LangGraph 的 create_react_agent 实现,工具包括简历检索、文档检索、保存文档
8. **问:上下文越来越长怎么办?** 答:双层治理 —— 超 2 万字提示手动压缩,超 4 万字服务端强制压缩;压缩 = LLM 把历史压成 200 字摘要(保留身份/结论/未完成事项)+ 最近 6 轮原文
9. **问:上传的文档存哪、存多久?** 答:解析出的 Markdown 不落盘(临时目录解析完即删);切片文本 + 向量存 pgvector,临时库挂会话 24h 自动清理,用户确认「长期记住」才转永久库 —— 按意图入库
10. **问:多 Agent 还是单 Agent?为什么?** 答:单 Agent + 多工具。现阶段任务简单,单 Agent 够用(YAGNI);多 Agent 编排(主管+专家)是任务变复杂后的演进方向,每多一个 Agent 就多几次 LLM 调用,成本跟着涨
11. **问:这个项目你遇到的最大难点是什么?**(必问,选一个主线讲)答:推荐讲**混合检索**这条线 —— 一开始纯向量检索,发现人名/缩写(如「林熹」)语义搜不到,向量对字面信息不敏感;解法是加一条 pg_trgm 关键词路 + RRF 融合,标定集从「搜不到」到 13/13。这条线有「发现问题 → 定位原因 → 设计解法 → 量化验证」完整闭环。备选:部署事故链(uv.lock 变脏卡部署)、上下文压缩(aput 静默拒绝)
12. **问:为什么用 LangGraph,不自己写循环?** 答:自己写「调工具→拿结果→再问 LLM」的循环也就几十行,但 LangGraph 额外给了三样:①状态机(图结构,加节点/分支不改主循环)②checkpointer 持久化(多轮记忆开箱即用)③astream_events(流式事件直接接 SSE)。省下的是「以后要加东西时的重构成本」;而且它是主流框架,面试官都认识
13. **问:如果用户量涨 100 倍,你的系统哪里先撑不住?** 答:①LLM 调用是最大成本和瓶颈 —— 要做模型计费/限流(积分体系已在计划)②文档解析是 CPU 密集,现在串行队列 + 名额 3,要换成分布式队列(如 Celery/RQ)③单台 2G 服务器,要上多实例 + 负载均衡;数据库可以读写分离。诚实说「现在规模用不上,但瓶颈在哪我很清楚」
14. **问:测试怎么保证质量的?** 答:TDD 为主 —— 先写失败测试再看它失败,再实现;分层验证:纯函数单测(不连库)→ 接口拦截测试 → 真库对照验证(标定集 13 题回归);线上踩坑后把坑固化成回归测试(如「asyncio 在 main 命名空间」锁启动崩溃)
