## 开场 30 秒

**一句话定位**:给个人博客做的 AI 智能助手 —— 会多轮对话、能回答「关于我」的问题(附出处)、还会读用户上传的 PDF/Word 文档,已上线 ai-myhome.space。

> 「这是一个 AI Agent 项目,基于 LangGraph + RAG 做的。它能干三件事:第一,像豆包一样多轮聊天,有账号有记忆;第二,关于我的简历问题,它通过检索我的知识库来回答,而不是瞎编——回答下面还会列出参考资料,点开能核对;第三,用户上传 PDF/Word 文档后,它可以读文档回答问题。整套是我独立开发的,Python + FastAPI 后端,PostgreSQL + pgvector 做向量检索,Nuxt 3 前端,已经上线,前后端加起来 125 个自动化测试。」

## 核心技术亮点

> 按「面试怎么讲」分 7 组,每组:技术点 + 一句亮点 + 一个必答问答。踩坑细节 → 文末附录。

### ① RAG 检索 —— 「回答要有出处」

- **切片**:LangChain 两段式(标题管结构 → 长度管切分),800 字上限 / 100 字重叠,标题进 metadata;短块只许同节合并
- **入库**:pgvector 双写双表(豆包 1024 维 / 智谱 2048 维,一表一模型),HNSW 索引;主提供方故障自动降级,「查不到」不算故障不降级
- **混合检索**:向量(语义「意思像」)+ pg_trgm 关键词(字面「有没有」)+ RRF 排名融合 —— 治缩写/专有名词搜不到;标定集 13/13
- **必答**「为什么混合检索?」→ 向量对字面信息不敏感,「bdms」被稀释;关键词路补字面,两路分数不同尺子,RRF 只比排名

### ② Agent 大脑 —— 「会调工具,不是纯聊天」

- LangGraph 图 = 状态机(状态/节点/条件边);`create_react_agent` 工具调用循环:LLM 决定调不调工具 → 执行 → 结果回填 → 再答
- 工具:search_profile(简历检索)、search_document / save_document(文档检索/转存)
- 来源收集:工具返回 Command 把命中写进图状态 → SSE sources 事件 → 前端参考资料块
- **必答**「Agent 和聊天机器人区别?」→ 工具调用循环 —— LLM 自己决定要不要查、查哪个,循环到能答为止;聊天机器人只会凭记忆答

### ③ 对话体验 —— 「流式 + 出处 + 错误可见」

- SSE:astream_events 每个 token 一个事件 → OpenAI 格式契约(正文 data + sources/chars 自定义事件块)→ 博客前端解析零改动
- 薄壳转发:博客 Nuxt 只透传,Authorization 原样带给 Agent 服务
- 错误可见:流中途失败发 `{"error":...}` 块,前端识别后红色横幅显示(2026-10-24 修复)
- **必答**「SSE 和 WebSocket?」→ SSE 单向(服务器推)、基于普通 HTTP、自动重连;聊天一问一答够用且更轻。保持 OpenAI 格式 = 前端零改动 + 生态兼容

### ④ 记忆与账号 —— 「conversation.id == thread_id」

- checkpointer:图状态按 thread_id 快照存 PG,前端只发最新一句,历史服务端恢复 —— 追问「那第二个呢」接得上
- 账号:bcrypt + JWT;会话归属防线(所有 SQL 带 `WHERE user_id = %s`,越权统一 404)
- 记忆治理:2 万字亮手动压缩按钮 + 4 万字强制兜底;压缩 = LLM 摘要(保留身份/结论/未完成)+ 最近 6 轮
- **必答**「记忆怎么恢复?」→ checkpointer 按 thread_id 快照存库,每次请求先恢复再跑;会话列表的 id 直接当 thread_id,零映射

### ⑤ 文档助手(M4)—— 「从读简历到读文件」

- MinerU basic/flash 双档位(PDF→OCR 小模型 / Office→确定性提取);独立 8001 服务,串行队列 + 名额 3 防过载
- 临时库(24h 自动清)/ 永久库两级;按意图入库 —— 用户确认「长期记住」才转永久
- **必答**「为什么解析独立一个服务?」→ 解析是 CPU 密集 + 秒级耗时,和问答同进程会堵事件循环;拆到 8001 串行排队

### ⑥ 可观测性与事故 —— 「出问题看得见」

- LangSmith:LLM/工具调用链、耗时、token 自动上报;`kb.search`/`search_profile` 手动 @traceable,瀑布图直接看到检索耗时与命中块;输入脱敏(只留查询词,连接串密码不上报)
- 豆包模型 EOS 事故:models 接口查状态(Retiring)→ 同 key embedding 正常排除欠费 → 官方公告确认 → 一行常量换 2.1-lite
- **必答**「事故说明什么?」→ ①大模型有生命周期,模型 ID 当配置看待、盯官方公告 ②流开始后 HTTP 状态码锁死 200,SSE 流内错误块是唯一通道,前后端都要实现这个契约 ③定位顺序:先排除账号/网络,再怀疑模型本身

### ⑦ 工程习惯 —— 「怎么保证质量」

- TDD 125 测试;分层验证:纯函数单测(FakeKB 注入)→ 接口测试(TestClient)→ 真库标定集(13 题回归)→ 协议级(MCP stdio 真握手)
- 拉取式自动部署:cron 每 5 分钟 git fetch 比对 commit 哈希,有更新才 pull + 重启 —— 国内连 GitHub 不稳,拉取天然重试、零外部依赖
- 安全:数据库只监听 127.0.0.1 + SSH 隧道访问;注册入口前后端双关(后端 403 才是真关闭)
- **必答**「为什么不用 GitHub Actions 推式部署?」→ 推式断了要重推、runner 回连国内服务器慢;拉取式每 5 分钟自动重试。版本对比直接用 git commit 哈希,不手写版本号文件

## 面试高频问答

1. **问:纯向量检索有什么缺点?** 答:对缩写/专有名词不敏感 —— 向量算语义相似,「bdms」这种词的字面信息被稀释,会命中语义像但无关的块
2. **问:怎么解决?** 答:混合检索:加一条 pg_trgm 关键词路做字面匹配,两路召回用 RRF 融合
3. **问:RRF 是什么?为什么不用加权求和?** 答:Reciprocal Rank Fusion,按排名融合(1/(60+rank) 求和)。两路的分数不是一个尺子没法直接加,排名可以
4. **问:word_similarity 和 similarity 的区别?** 答:分母不同 —— similarity 用长文本当分母,短问长文永远趋近 0;word_similarity 用查询词当分母,衡量「查询词在块里出现几成」
5. **问:pg_trgm 和 GIN 索引是干什么的?** 答:pg_trgm 把文本切成连续三元组;GIN 是倒排索引(词 → 出现位置),专门加速「哪些行包含某个值」,和 B+ 树是两种思路
6. **问:为什么数据库只监听 127.0.0.1?** 答:最小暴露面 + SSH 隧道访问,外网连 5432 都碰不到
7. **问:Agent 和普通聊天机器人有什么区别?** 答:Agent 有工具调用循环 —— LLM 自己决定「要不要查资料、查哪个」,循环到能回答为止。本项目用 LangGraph 的 create_react_agent,工具包括简历检索、文档检索、保存文档
8. **问:上下文越来越长怎么办?** 答:双层治理 —— 超 2 万字提示手动压缩,超 4 万字服务端强制压缩;压缩 = LLM 把历史压成 200 字摘要(保留身份/结论/未完成事项)+ 最近 6 轮原文
9. **问:上传的文档存哪、存多久?** 答:解析出的 Markdown 不落盘(解析完即删);切片文本 + 向量存 pgvector,临时库挂会话 24h 自动清理,用户确认「长期记住」才转永久库 —— 按意图入库
10. **问:多 Agent 还是单 Agent?为什么?** 答:单 Agent + 多工具。现阶段任务简单,单 Agent 够用(YAGNI);多 Agent 编排是任务变复杂后的演进方向,每多一个 Agent 就多几次 LLM 调用,成本跟着涨
11. **问:这个项目你遇到的最大难点是什么?**(必问,选一条主线讲)答:推荐讲**混合检索**这条线 —— 一开始纯向量检索,发现人名/缩写(如「林熹」)语义搜不到;解法是加一条 pg_trgm 关键词路 + RRF 融合,标定集从「搜不到」到 13/13。这条线有「发现问题 → 定位原因 → 设计解法 → 量化验证」完整闭环。备选:部署事故链(uv.lock 变脏卡部署)、上下文压缩(aput 静默拒绝)
12. **问:为什么用 LangGraph,不自己写循环?** 答:自己写「调工具→拿结果→再问 LLM」的循环也就几十行,但 LangGraph 额外给了三样:①状态机(图结构,加节点/分支不改主循环)②checkpointer 持久化(多轮记忆开箱即用)③astream_events(流式事件直接接 SSE)。省下的是「以后要加东西时的重构成本」;而且它是主流框架,面试官都认识
13. **问:如果用户量涨 100 倍,你的系统哪里先撑不住?** 答:①LLM 调用是最大成本和瓶颈 —— 方向是模型计费/限流 ②文档解析是 CPU 密集,现在串行队列 + 名额 3,要换成分布式队列(如 Celery/RQ)③单台 2G 服务器,要上多实例 + 负载均衡;数据库可以读写分离。诚实说「现在规模用不上,但瓶颈在哪我很清楚」
14. **问:测试怎么保证质量的?** 答:TDD 为主 —— 先写失败测试再看它失败,再实现;分层验证:纯函数单测(不连库)→ 接口拦截测试 → 真库对照验证(标定集 13 题回归);线上踩坑后把坑固化成回归测试

## 框架与概念题

**Q:LangGraph 的「图」是什么?状态/节点/边怎么理解?**
答:图 = 状态机。状态(state)是对话过程中共享的数据(消息列表、收集的来源);节点是处理函数(调 LLM、执行工具);边决定下一步(普通边固定、条件边按状态分支)。工具调用循环就是「LLM 节点 → 条件边 → 工具节点 → 回 LLM」这个小环。

**Q:为什么对话历史能跨请求恢复?checkpointer 原理?**
答:每次对话结束,checkpointer 把图状态按 thread_id 快照存进 PostgreSQL;下次同 thread_id 的请求先恢复状态再继续跑。所以前端只发最新一句,历史由服务端补 —— 会话列表的 id 直接当 thread_id,零映射。

**Q:RAG 是什么?和微调(fine-tuning)的区别?**
答:RAG = 检索增强生成:不训练模型,知识放在外部库,回答前先检索相关段落喂给模型。微调 = 改模型权重把知识「记」进去。RAG 的优势:知识可随时更新(改文件重灌就行)、答案可溯源(有参考资料)、成本低。简历这种会变、需要证据的内容,RAG 是正解;微调适合风格/格式这类「能力」,不适合「事实」。

**Q:embedding 是什么?向量检索为什么能查到「意思相近」?**
答:embedding 模型把文字映射成高维向量,语义相近的文字在向量空间里距离近(本项目用余弦距离)。查询词同样转成向量,在库里找最近的几块 —— 这就是「意思像」的数学基础。注意:向量对字面敏感度低,所以要配关键词检索。

**Q:为什么对话要流式(SSE)?怎么实现的?**
答:LLM 完整回答要 15~30 秒,不流式用户盯着白屏以为坏了;流式首字节 0.14 秒就有反馈。实现:LangGraph 的 astream_events 每吐一个 token 一个事件,服务端翻译成 OpenAI 格式 SSE,Nginx 关 proxy_buffering 保证逐字透传。

**Q:temperature 是什么?豆包的 thinking 参数又是干什么的?**
答:temperature 控制采样随机性:低 = 答案稳定保守,高 = 有创造性但容易跑偏。对话助手取 0.7 平衡。豆包的 thinking 是「先想后答」模式,会先输出一大段思考过程再给答案 —— 聊天场景要的是立即出字,所以显式传 `thinking: disabled` 关掉。

**Q:MCP 和 Function Calling 有什么区别?**
答:Function Calling 是模型在**一次对话内**调用你声明的工具;MCP 是**跨应用**的工具开放协议 —— 把你的工具按标准接口暴露,任何支持 MCP 的客户端(Claude Code/Cursor)都能发现并调用。项目里同一个 search_profile:绑进 LangGraph 是工具,注册成 MCP Server 后 Claude Code 也能查简历 —— 能力一次实现,多入口复用。

**Q:为什么这个项目用 Python 而不是 Node?**
答:生态决定 —— LangChain/LangGraph/LangSmith/pgvector/MinerU 的 Python 支持都是第一梯队,AI 工具链基本在 Python 侧;Node 是我熟的主场(管道项目)。两个项目正好证明「按场景选语言,不被一门语言绑住」。

**Q:怎么防止大模型幻觉(瞎编简历内容)?**
答:三道防线:①知识只来自检索命中,检索不到就明说「没找到」,不许模型凭记忆编 ②答案附参考资料,访客可核对原文 ③混合检索提高召回质量(专有名词靠关键词路命中),喂进去的内容对了,答案才可能对。

**Q:怎么评测 RAG 质量?**
答:标定集回归 —— 手工整理 13 个「有预期答案的问题」(专有名词、经历细节、教育背景各类型),每次改检索逻辑跑一遍,13/13 才算通过。工程上这就是 RAG 的最小评测集;还发现过 embedding 非确定性噪音(同代码两次运行排名互换),所以对比实验要先排除随机性再定罪。

**Q:LLM 调用成本怎么控制?**
答:①上下文治理:历史压成摘要,每轮重发的 token 降一个量级(4 万字 → 3 千字)②检索只喂 top 块,不塞全文 ③按档选模型:聊天用 lite 档,便宜够用。积分计费体系在计划里,是下一步。诚实说:个人项目量小成本无感,但这些机制是「量大了也不慌」的提前量。

5. 会话记忆怎么实现的?
   **答**:checkpointer 按 thread_id 把图状态快照存 PG;登录用户 conversation.id == thread_id,前端只发最新一句。访客不带 session_id 则无记忆(产品决策)。
6. 上下文越来越长怎么办?
   **答**:双层治理 —— 2 万字亮手动压缩按钮,4 万字服务端强制压;压 = LLM 摘要(保留身份/结论/未完成)+ 最近 6 轮原文。
7. MCP 是什么?为什么函数一行不改?
   **答**:AI 工具的开放标准(类比 USB-C)。tools.py 只写检索逻辑,绑 LangGraph / 注册 MCP 都是外面包一层 —— 一套能力多个入口。
8. PDF 怎么解析的?basic/flash 区别?
   **答**:MinerU 按后缀选档位:PDF/图片走 basic(ONNX 小模型 OCR,CPU 可跑),Office 走 flash(确定性文本提取,不跑神经网络)。解析独立成 8001 服务,串行队列 + 名额 3,防 CPU 密集任务拖垮问答服务。
9. 怎么防越权/篡改?
   **答**:会话归属防线 —— 所有会话 SQL 带 `WHERE user_id = %s`,取不到统一 404 不暴露存在性;JWT 由服务端签名,userId 不可伪造。
10. 豆包模型下线那次怎么定位的?
    **答**:先查 `/api/v3/models` 看模型状态(Retiring)→ 同 key embedding 正常排除欠费 → 官方公告确认 EOS → 换迁移目标 2.1-lite,一行常量修复;顺带修了前端不显示 SSE 错误块的缺陷。
11. LangSmith 追踪什么?为什么不用日志?
    **答**:每次对话的调用链树(节点/耗时/token),retriever 和 tool 手动 @traceable 标出检索命中;输入脱敏。日志是零散字符串,追踪是有结构、可聚合检索的树。
12. SSE 和 WebSocket 区别?为什么选 SSE?
    **答**:SSE 单向(服务器→客户端)、基于普通 HTTP、自动重连,聊天「一问一答流式」够用且更轻;WebSocket 双向全双工。协议保持 OpenAI 格式,前端零改动。
13. 测试怎么分层?
    **答**:纯函数单测(FakeKB 注入)→ 接口测试(TestClient 拦 401/422)→ 真库对照(标定集 13 题回归)→ 协议级验证(MCP stdio 真握手)。TDD:先写失败测试再看它失败。
14. 部署怎么自动化?
    **答**:push 到 GitHub → 服务器 cron 每 5 分钟 git fetch 比对 commit 哈希 → 有更新才 pull --ff-only + pm2 restart。选拉取式:国内连 GitHub 不稳,拉取天然重试、零外部依赖。
15. 用户量涨 100 倍哪里先撑不住?
    **答**:①LLM 调用是最大成本和瓶颈 → 计费/限流 ②文档解析 CPU 密集 → 分布式队列 ③单机 2G → 多实例 + 负载均衡、数据库读写分离。诚实说现在规模用不上,但瓶颈在哪很清楚。
